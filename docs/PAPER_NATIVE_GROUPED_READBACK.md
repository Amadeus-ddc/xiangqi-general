# 完整原生复核按棋局执行

大规模规则题复核要重算每题答案，并检查局面的完整历史。随机分发同一棋局的不同局面，会让多个进程各自重复验证共同历史。12个实际长历史的三轮测量各约7.2秒，几乎全部耗时在原生历史验证；这是局部性能测量。

`course_render_spool.render_grouped_positions` 保持原来的抽题顺序、随机种子和累计频率更新。它先把原生查询草稿保存到独立SQLite暂存文件，按棋局分发，长历史优先，使原有纯规则缓存能复用共同前缀。每个选中历史仍调用原`course_rendering._native_record_batch`，每题仍调用原生答案函数。完成的答案另存，最终按原选择序号输出。未经过原生检查的草稿不会被输出；工作进程报错、数量或顺序不匹配会终止运行，部分文件保留。

执行器要求新的暂存目录和正整数工作进程数、单次局面组上限。它不训练模型，也不修改题型预算、棋局分割、标签、课程配方或已有源码快照。

## 实际检查

全套1514项CPU检查通过。新增测试检查完整读取的字节、抽题与答案顺序、已有暂存目录保护、参数拒收、伪造历史及非法未来变化。

使用原冻结的95份数学模块完成207道构造控制题的完整复核，训练103、验证52、测试52；各划分均覆盖全部26种题型，所有题型位置预算填满。按棋局执行与原实现的完整验证结果相同，完整未来隔离仍执行。另36题控制核对已验证目录复用、目录副本及原源码不变。这些题仅用于控制，没有进入正式语料。

由12个实际历史构造192个合法前缀，四进程重复三次，全部答案字节和累计频率相同。局部耗时分别缩短1.35、1.94、1.51倍，工作进程CPU用量约为原来的37%。它不证明10833161道生产题的吞吐或学生质量。
