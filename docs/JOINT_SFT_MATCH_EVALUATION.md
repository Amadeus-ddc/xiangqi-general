# 联合讲解模型的同设置对弈

旧课问答和讲解有效率不能替代实际下棋。新的联合讲解候选将沿用原初始讲解模型的完整开发对弈设置，再比较两份原始结果。新模型3072步训练及所选2304步的课程／完整讲解评测均已完成，已通过对弈依赖检查，正在等共享启动资源，本项对弈尚无成绩。

| 设置 | 固定范围 |
| --- | --- |
| 开局 | 原64个验证开局，每个12半回合 |
| 模型颜色 | 每个开局交换红黑 |
| 引擎预算 | 每步100、1000、10000节点 |
| 总场次 | 64 × 2 × 3 = 384 |
| 每局长度 | 最多新增256半回合，截断单列 |
| 模型动作 | 原始完整讲解生成，不加合法走法约束，不用引擎替换非法输出 |
| 执行和判分 | 与原基线相同的固定源码及原生历史规则 |

原生准备已实际核对64个开局和384个场次。配置相对原基线只更换对应的新讲解复查配置和物理GPU编号；节点预算、原开局、红黑、长度、模型动作和引擎身份保持。两个CLI帮助入口通过；这些准备没有加载学生或教师、初始化CUDA或生成比赛成绩。

联合SFT及其2600题课程回放、三组384条讲解和正文辅助评审均已完成，见[完整开发复查](JOINT_SFT_FULL_DEVELOPMENT_REVIEW.md)。任务已通过这些依赖，仍须在模型加载前核对实际所选2304步权重与完整训练证明；原1792步模型独立保留。

## 启动与共享显存

本服务器新对弈与教师使用同一个启动资源锁，GPU 0空闲至少32768MiB才开始。观察到子进程新增的原始模型回合后，释放启动锁；后续教师根据实际空闲显存安排。现存回合不能冒充恢复后的新模型加载；子进程正常退出或失败也会释放锁。比赛过程中保留原始模型回答，不改写比赛产物。

[启动协调工具](../scripts/match_startup_lease.py)只处理进程、日志和启动锁，不参与模型生成、判分或合法走法修复。四种真实OS进程测试覆盖首次启动、带旧回合的恢复、无需新回合即完成，以及子进程失败；日志中的URL和地址会被遮蔽。

## 同场次比较与证据范围

新旧各384局都形成终止或截断记录后，按开局、红黑和引擎预算逐场对齐，重新读取原始对局和完成清单。分别报告胜负和、非法弃负、讲解合同及截断；只有一对比赛都完成时才计算该对比分变化。截断不记作和棋，不据节点预算换算人类等级分。

64个开局的颜色交换和不同预算属于相关观测。比较的是两个不同训练配方得到的候选，不声称单一训练变化的因果效应。此处只用验证开局，最终独立测试继续保留；完成开发对弈也不能替代最终棋力、教学与模型交付验收。

服务器运行记录在`runs/joint-replay-full-matches-v1/`，查看`state.json`、`launcher-verification.json`、`baseline/state.json`、`comparison.json`与`exit.json`。配置、固定源码、输入和进程身份分别保存在`matches.json`、`plan.json`、`launch.json`及`owner.json`；任务在`xqgeneral-joint-replay-full-matches-v1`的tmux会话中自动接续。不要另起同一份存活任务；恢复前核实原进程确已结束，并保持原输入、源码和比赛合同。

启动协调工具的四项进程回归、2053项完整CPU检查与构建／发布检查通过。软件和运行准备检查不产生新模型成绩。
