# 完整读回后接入输入哈希复用

[`verified_input_continuation.py`](../scripts/templates/verified_input_continuation.py) 是长期准备任务的接续模板。它等已有来源、缓存和基座的完整读回完成，随后在显式[输入核验会话](VERIFIED_INPUT_DIGESTS.md)内运行原准备入口。原入口、配方及旧源码快照保留；执行时使用单独声明、已经验证的派生源码。

这项接续控制解决启动和中断恢复问题。它不改变模型、训练损失、采样、优化器、课程预算或选模，也不构成四课完成或棋力证明。

## 启动条件

计划必须将执行入口、过程控制辅助文件、资格证明、原准备入口、原所有权证明、种子候选、完整预检及两份原始签名向量逐字节绑定。执行源码目录按全部 Python 文件的 SHA256 精确核对。路径限制在指定项目内，运行状态放在项目的 `runs/` 下。

`process_helper` 提供四个有界接口：`identity(pid)` 返回 PID、启动刻度、父 PID、状态及命令行 SHA256；`same(identity, parent=True)` 核对身份；`send(identity, signal)` 使用 pidfd 并重新核对身份；`tree(identity)` 只遍历该进程当前拥有的后代。模板不会按通用进程名停止其他任务。新子进程要先确认预期命令行，避免 `exec` 过渡时读到空命令行而误认退出。

完整读回需要同时满足：

- 清单种类为 `recorded_foundation_source_and_cache_readback`，状态为 `complete`，执行源码与计划一致。
- 所有计划声明的计数和验证字段相同，明确记录没有进行学生训练；读回输出及指定的小型原始前序文件重新核验字节。
- 原读回进程已结束，原父进程与已完成的所有权证明一致、没有子进程，也没有既有暂停；正式课程输出尚不存在。
- 独立恢复进程已启动并确认当前控制器身份。

默认策略满足以上条件后，才记录自己的暂停意图并暂停原父进程；暂停确认后再次核对完整读回。尚未完成的读回和已经存在的课程均不会被接管。

NAS读取中的进程可能处于磁盘等待，内核需要等读取返回才能确认整个线程组暂停。确认阶段持续检查同一进程身份与终止状态，等待明确的`T`状态，不以固定十秒认定暂停失败。独立恢复进程仍只在控制器实际结束后取消自己登记的暂停意图；尚未确认暂停时不会发布输入证明或启动准备子进程。

### tmux直接窗口进程的交接

tmux会自动向被暂停的直接窗口进程发送SIGCONT，见[官方server_child_stopped实现](https://github.com/tmux/tmux/blob/master/server.c)。因此，延长等待本身无法暂停这类原父进程。

对此可以显式声明`handoff_policy=retire_completed_restartable_preparation`。额外的`restartable_preparation_admission`必须在项目内并逐字节绑定，包含原进程身份、原冻结入口哈希、完整读回哈希，以及已完成预检／读回和其余声明阶段的清单哈希。该策略只接受完整证明已就绪、没有子进程、没有正式课程输出的准备进程。

程序先持久记录`preparation_handoff_committed`及原进程退役意图，再按完整身份结束原准备进程。此时只取得准备工作所有权，`committed`仍为false，不能开始训练。新准备成功及原四卡容量检查通过后，才提交训练许可。该策略不要求暂停tmux服务器，也不修改原进程的源码或其他会话。

如果准备交接提交后控制器结束，恢复进程完成已登记的原准备退役、停止本次准备子进程并保存零权重的中止输出，释放租约。旧准备进程不再恢复。使用相同计划的`--resume-committed`可从这次已提交的准备交接继续；此时要求原进程及登记子进程均已结束、租约已释放、正式输出已由回滚归档，且仍没有训练许可。准备和容量检查会重新执行。

种子候选仍不可直接消费。发布前会将其与完整预检的 `inputs`、成功完整哈希时保存的前后签名逐项比较，并限定在项目 `data/`、`models/` 的不可变输入。当前签名仍须匹配原签名；禁止给预期哈希附上后来取得的任意签名。运行时重写的配置和新生成产物继续使用正常哈希。

## 执行与恢复

模板调用原准备入口的 `main()`，只替换这个入口自身的 `subprocess` 引用，把正式课程 CLI 路由到已经验证的 GPU 源码与输入证明。全局 `subprocess` 模块不被改写。子进程真实执行、返回真实退出码；没有伪造成功状态。

准备子进程在 `exec` 前登记自身启动和执行身份，并核验活的父控制器、请求内容哈希及本次启动标识。请求文件仅含参数和状态，不保存整个环境变量。新训练只能在原有四卡容量检查通过、并提交切换后启动。条件容量证明及四卡连续空闲检查沿用原实现。

默认暂停策略在训练许可提交前失败时，独立恢复进程停止本次登记的准备子进程，保存本次新建且没有权重的准备目录，再恢复自己暂停的原父进程。显式退役策略按上一节保存并恢复已提交的准备交接。既有暂停不被认领；没有自己的准备输出时也不会移动原任务创建的文件。

切换提交后，原父进程按已记录的完整身份结束。控制器后续异常不会恢复旧父进程，也不会杀掉仍在训练的已登记子进程。恢复依据真实进程身份和存活状态；活的控制器即使处于磁盘等待或暂停，也不会因为观察时间过期被替换。

启动和恢复都应放在 tmux 中，例如在私有运行目录冻结模板及项目专用计划后：

```bash
python /path/to/run/entry.py --plan /path/to/run/plan.json
```

`state.json`、`lease.json`、`watchdog-state.json`、`watchdog.log`、`accepted-readback.json` 和每次独立的 `formal-capacity-observations-*.jsonl` 记录实际阶段、所有者和容量检查。原准备入口继续保存真实课程日志和输出。

已提交的控制器结束且其租约释放后，先检查登记的训练子进程。如果它仍存活，继续观察原进程。只有原父进程和登记的训练子进程均已结束，才使用相同源码、计划及原课程目录恢复：

```bash
python /path/to/run/entry.py --plan /path/to/run/plan.json --resume-committed
```

恢复会保存旧租约，核验同份完整读回，重跑原准备入口和四卡容量检查，再由课程自身的精确配置、源码、世界大小及检查点合同决定续训。每次容量观察使用独立文件。没有提交准备交接或训练许可的回滚目录保留，需在新的运行目录建立新计划。

## 验证范围

[`test_verified_input_continuation.py`](../tests/test_verified_input_continuation.py) 使用真实 Linux 进程、pidfd 信号、`exec` 和真实输入证明消费，覆盖正常切换、未完成读回等待、变化或不匹配的证明、既有课程、已有暂停、准备失败回滚、提交后错误、控制器死亡、存活但暂停的控制器、已登记训练保护以及显式恢复。

这些进程测试使用明确的课程和容量替身，没有执行神经训练或测试 GPU 显存。实际四卡数值资格另由固定的预训练模型与专家特征验证：原连续训练、新连续训练和新断点恢复的参数、优化器、随机状态、数据状态及轨迹逐位一致，见[输入复用证据](../evidence/verified-input-digests-real-v1.json)。接续模板的检查和正式部署状态须分别记录。
